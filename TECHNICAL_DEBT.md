# Auditoria Técnica — GestCondo

Data: 2026-07-06. **Atualização 2026-07-06 (Fase 1):** o repositório foi inicializado com git (primeiro commit `0b9154e`), o `pnpm lint` foi corrigido (T1) e os 13/14 erros de tipo pré-existentes de `@base-ui/react` foram corrigidos com `ignoreBuildErrors` removido (T2, ver abaixo) — os restantes achados desta secção continuam por endereçar.

## 1. Stack e arquitetura

- **Framework:** Next.js 16.2.6 (App Router, Turbopack), React 19.
- **Linguagem:** TypeScript 5.7, `strict: true` no `tsconfig.json`. `typescript.ignoreBuildErrors: true` existia no `next.config.mjs` e anulava esse rigor no build — **removido 2026-07-06** depois de corrigidos os erros de tipo subjacentes (ver T2 abaixo e `SECURITY_AUDIT.md` S15).
- **Base de dados:** PostgreSQL (Neon) via `pg` + Drizzle ORM 0.45, com `drizzle-kit` e migrações versionadas em `drizzle/` desde 2026-07-06 (ver T4). São 28 migrações aplicadas a 2026-07-25 (`pnpm db:check-drift` confirmado "OK" nessa data), em duas bases de dados distintas (branches `development` e `production`) — a aplicação a produção continua a ser manual, ver D8.
- **Autenticação:** better-auth 1.6.23, email+password apenas.
- **UI:** Tailwind CSS v4 + `@base-ui/react` (primitivos, via um wrapper ao estilo shadcn) + `lucide-react`.
- **Sem backend separado**: tudo corre dentro do próprio Next.js via Server Actions (`app/actions/*.ts`) e uma única rota de API (`app/api/auth/[...all]/route.ts`, exclusiva do better-auth). Não há uma camada de "serviço"/domínio separada da camada de acesso a dados — as server actions falam diretamente com o Drizzle.
- **Controlo de versões:** ✅ resolvido 2026-07-06 — repositório git (commit inicial `0b9154e`, branch `main`), publicado no GitHub em `Rjsoft/GestCondo`. Continua sem processo formal de code review.
- **CI/CD:** ✅ resolvido 2026-07-06, **ativo desde 2026-07-24** — `.github/workflows/ci.yml` (lint, typecheck, testes unitários, build) corre em cada push/PR para `main`, confirmado a correr no PR #1. O deploy para produção na Vercel é automático a cada push para `main`; **a aplicação de migrações não é**, ver D8.
- **Sem `LICENSE`.** O `README.md` existe desde que o repositório foi publicado.

### É uma arquitetura adequada para evoluir para SaaS multi-condomínio?

O padrão (Next.js App Router + Server Actions + Drizzle + better-auth) é uma escolha razoável e atual, capaz de suportar um SaaS a sério. À data desta auditoria, o obstáculo não era a stack mas o modelo de dados e a ausência de multi-tenancy — **ambos resolvidos em 2026-07-06** (schema `condominio` + `condominioId`, autorização com âmbito de condomínio em todas as server actions; ver `SECURITY_AUDIT.md` S9 e D1 abaixo), com o fluxo de onboarding para um segundo condomínio acrescentado em 2026-07-22. Não houve necessidade de mudar de framework.

## 2. Qualidade do código existente

Dentro do que está construído, a qualidade é boa para o estágio de maturidade do projeto:

- Padrão consistente entre módulos (página lista + diálogo de criação + componente de ações), fácil de replicar para novos módulos.
- Sem duplicação séria de lógica de negócio.
- Autorização feita de forma explícita e legível em cada server action (`requireAdmin()`, `requireMembroAprovado()`), não escondida em middleware opaco.
- Nomenclatura em português consistente em toda a aplicação (dados, UI, mensagens de erro) — bom para o público-alvo.
- Sem uso de `any` nem gambiarras de tipo encontradas fora dos erros de tipo pré-existentes descritos abaixo.

Testado contra a BD de dev (28/28, OK) e contra a ausência de `DATABASE_URL` (salta sem bloquear). **Decisão de desenho**: compara por contagem, não por hash — testar a comparação por hash (reutilizando `readMigrationFiles` de `drizzle-orm/migrator`) revelou que a migração `0026` tem em dev um hash gravado que já não bate certo com o hash atual do ficheiro (mesma deriva de fim-de-linha já vista na `0025`); comparar por hash teria bloqueado deploys legítimos já hoje por esse motivo, sem relação com uma migração realmente em falta. **Continua a não substituir o processo**: a mudança de processo recomendada abaixo mantém-se válida — este gate é uma rede de segurança adicional, não uma automação da aplicação de migrações (isso continua a exigir autorização explícita, ver `docs/PROCEDIMENTO_MIGRACAO_PRODUCAO.md`). | **Mudança de processo recomendada, não só técnica**: a partir de agora, qualquer PR/commit para `main` que inclua uma migração de schema deve ter a migração aplicada a produção **antes ou imediatamente depois** do push — nunca com um intervalo de "vou tratar disso depois", porque o deploy já aconteceu automaticamente nesse intervalo. O gate de build (`check-pending-migrations.mjs`) agora impede que esse intervalo resulte numa versão avariada em produção, mas não elimina a necessidade de aplicar a migração — só evita que o site fique servido com um schema incompatível enquanto isso não acontece. Item aberto à parte, não bloqueador: a deriva de hash da migração `0026` em dev (achado durante este trabalho) pode valer a pena investigar/corrigir na bookkeeping (`drizzle.__drizzle_migrations`) numa sessão dedicada, como já foi feito para a `0025`. |

## 6. Conclusão desta secção

O código que existe é limpo, consistente e de fácil manutenção — não há indício de que seja necessário reescrever o que já está feito. À data desta auditoria, o risco técnico principal estava em quatro ausências estruturais: controlo de versões, testes automatizados, migrações de schema versionadas e o modelo de dados multi-tenant. **As quatro foram fechadas em 2026-07-06.**

O risco técnico que **permanece** é outro, e está identificado nas linhas próprias acima: a aplicação de migrações a produção continua manual (D8 — já causou três incidentes reais, o mais recente derrubando todo o módulo financeiro em produção), o `storage` do rate limiting não é partilhado entre instâncias (`SECURITY_AUDIT.md` S5), não há `updatedAt` consistente (D6), e a janela de recuperação da Neon no plano atual é de 6 horas (D7).
